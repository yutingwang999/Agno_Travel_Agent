# Design

## Context

- Every step emits its event through `build_sse_event` and writes a trace with `write_trace`; trace writing already swallows exceptions.
- `cag_matcher.match_category`, `generate._call_llm` and `validate_output._call_llm` have no try/except, so exceptions pass through Agno all the way up to FastAPI and show up as an interrupted request.
- In the template fallback branch, `generate_executor` only updates `template_text` and `template_version`, not `template_key` (`generate.py:240-247`).
- `parse_llm_output` first strips markdown code fences, then runs `json.loads`, then Pydantic validation, and finally checks whether `len(daily_itinerary)` equals the `trip_length_days` in the output.
- The input has only Pydantic field validation; `travel_style` is free text and is spliced straight into the prompt.
- `build-evaluation-harness` has already defined the per-budget-level daily cost caps in `config.py`. The v0.1.0 templates never state them: the model sees only "a moderate budget", so the baseline's "within budget" (59.6%) measures how often the model's own guess happens to fall under a number it was never given.
- Agno's `Workflow` defaults to `telemetry=True` and sends one event per run (workflow id, session id, run id, db type) to `os-api.agno.com`. The `AGNO_TELEMETRY` environment variable, when set, overrides the constructor value, and it is read again before every send. `tests/conftest.py` already sets `AGNO_TELEMETRY=false` for tests (`isolate-test-database`); the running app still sends it.

## Goals / Non-Goals

**Goals:**
- When an external dependency (Gemini, the database) fails, every step emits `status="error"` or an explicit degraded result instead of raising an unhandled exception.
- Every business rule that can be checked by code is checked by code, without relying on the LLM behaving.
- Obviously unreasonable input is stopped before it enters the workflow.

**Non-Goals:**
- No automatic retry and backoff on LLM call failure.
- No runtime check of "attractions are in the destination" (requires geocoding; see roadmap item 4).
- Input guardrails are simple rules only, with no model-based injection detection; they do not aim to stop every attack.

## Decisions

1. **An embedding failure is treated as "no match" and takes the existing empty-data fallback path** (`family`, `confidence_score=0.0`, `is_fallback=true`). Under the current routing, 0.0 goes to the retrieval branch, consistent with the safe default of "get more context when information is insufficient". Alternative: return an error and stop the workflow — this contradicts "CAG: fallback to default category" in DESIGN.md.

2. **On LLM failure, record only the exception type; do not put the raw exception text into the SSE event.** The event's `error` field says `"LLM call failed: <ExceptionType>"`; the full details go into the log, to avoid exposing API error details to the frontend.

3. **validate_output checks the status of the generate event first.** If it is `error`, it emits an error event directly, without parsing or calling the correction LLM.

4. **Structured output uses `response_mime_type="application/json"` plus `response_schema`, with the schema generated from `ItineraryOutput`.** The code-fence stripping logic is kept as a fallback (e.g. when switching models, or when the schema is not supported). Alternative: rely only on the JSON example in the prompt — this is what v0.1.0 does; its format failure rate is to be quantified by the evaluation.
   - **Experiment (task 3.1, 2026-10-29, google-genai 1.60.0, `gemini-3.1-flash-lite`)**: the v3 high-confidence prompt (Sydney, 3 days, moderate) sent twice each with no schema, with `response_schema=ItineraryOutput` (the Pydantic class; the SDK converts it to Gemini's schema), and with `response_json_schema=ItineraryOutput.model_json_schema()`. All six replies were unfenced JSON that `parse_llm_output` accepted, with the fields in schema order; no call failed. The current model needs nothing beyond `List`, `int`, `float` and `str`, so no hand-written schema is needed. Outputs with a schema were shorter (410–438 output tokens against 497–506 without), which the evaluation of (c) will show in the claim counts if it matters.
   - **Choice**: `response_schema=ItineraryOutput`, the SDK's documented path for a Pydantic model. `response_json_schema` would work equally and stays the fallback if a later model rejects the converted schema. The response text is still parsed and validated by `parse_llm_output`, not taken from `response.parsed`, so the fence-stripping fallback and the same error messages apply to every provider.
   - **The JSON example in the templates stays** (no new template version in this section). The templates write it with doubled braces (`{{` / `}}`, `str.format` escaping), but `_format_template` substitutes with a regex and does not unescape them, so the model has always received doubled braces; v0.1.0 nonetheless had a 100% format pass rate, and with a response schema the example only describes fields. Changing it would add a prompt change to step (c) of task 6.3; `rebuild-rag` writes its new template with single braces instead (they survive `_format_template`, which replaces only identifier placeholders).

5. **All business rules sit in one rule list after `parse_llm_output`; any rule failing counts as a validation failure and enters the existing corrective retry flow.** The error message states which rule and the concrete values, so the correction prompt can act on it. Each rule is a pure function, easy to test on its own.
   - **Days**: `len(daily_itinerary) == trip_length_days == requested trip_length`.
   - **Cost consistency**: `|Σ estimated_cost_aud − total_estimated_cost_aud| ≤ max(1 AUD, 1% of the total cost)`. A failure goes through the correction call like every other rule. Alternative considered (2026-10-31): code sets the total to the daily sum, saving a correction call and never losing an itinerary to a failed correction — but the corrected total would need the budget rule again and the event would have to say the number was changed. Not adopted while the rule rarely fires (0 inconsistent itineraries in the baseline, (a) and (b) runs); revisit if step (c) of task 6.3 shows a high trigger rate.
   - **Budget ceiling**: `total_estimated_cost_aud (per person) ≤ daily ceiling × number of days`, where the daily ceiling is the request's (decision 13); no ceiling, no check. The failure message states both numbers, e.g. `Business rule failed: budget — total 1,200 AUD per person exceeds the ceiling of 600 AUD (200 per day × 3 days)`, so the correction call knows the target.
   - **Unsupported specifics**: in the text fields (morning / afternoon / evening / key_tips), find two kinds of content — opening-hours statements (a time appearing together with open / opens / opening / close / closes) and currency amounts (`$25`, `AUD 30`, `A$40`, etc.). Each occurrence must appear in this request's knowledge context (ignoring case and whitespace), otherwise the rule fails. Numeric fields such as `estimated_cost_aud` are estimates and are not subject to this rule. Itinerary scheduling such as "depart at 9am" is not an opening-hours statement and is unaffected. The request's own budget figures (the daily ceiling and the trip ceiling) also count as supported: the step (c) runs of task 6.3 showed the model repeating the ceiling that template v3 gives it ("stay under the 70 AUD daily limit", e024 and e034), and the rule rejected it as an invented price, costing two needless correction calls in 146 requests. Times and amounts are compared by value, not as text, so "9:30am" matches "09:30" and "$25" matches "AUD 25".

6. **Input guardrails sit in the request-validation layer before intake; on failure they return 422 with a reason code.** This way blocked requests consume no LLM calls, and the evaluation harness counts them as `refuse`.
   - **Rejection body**: `{"reason": <code>, "detail": <fixed message>}`, produced by one exception class and an exception handler. `detail` stays a human-readable string, so the frontend shows it unchanged, and the presence of `reason` separates a guard rejection from FastAPI's validation errors (`{"detail": [...]}`). The message is fixed per code and never echoes the input or names the matched pattern or field: telling a caller which rule fired would show how to get around it.
     Alternatives: the code inside `detail` (`HTTPException(422, detail={...})`) — `detail` would be a string, list or object depending on the error and the frontend would show `[object Object]`; FastAPI's validation-error list with the code as `type` — mixes refusals with field errors and exposes the field via `loc`; RFC 9457 Problem Details — a second error format for the same endpoint, heavier than needed.
   - **Fixed messages** (confirmed 2026-10-28): `destination_out_of_scope` → "Please enter one specific destination in Australia, such as Sydney, Cairns or Tasmania."; `input_rejected` → "Your request could not be processed. Please rephrase it and try again." The destination message ("one" added 2026-10-31, since a request naming two places is refused with it too) is worded to fit a foreign city ("Paris"), two destinations ("Sydney, Melbourne") and a destination too vague to look up ("Australia", "the east coast", "somewhere warm"), so one code covers both without a list of vague words. Alternative: a third code `destination_too_vague` — another public API value and a list of "vague" names to maintain; asking a clarifying question is left to roadmap item 3.
   - **Out-of-scope destination**: the normalised destination must appear in `data/places/australia.tsv`. Each line of the file is "acceptable name → canonical lowercase English name". On a match the destination is replaced with the canonical name, so downstream retrieval and destination filtering only need to handle English names. The cost is that small places may be wrongly rejected, which the README states; roadmap items 3 (LLM request parsing) and 4 (Nominatim) can replace this approach.
     - **Sources**: Australian rows of GeoNames `cities1000` (places with population ≥ 1000, CC BY 4.0), primary and ASCII names only — the alternate names include romanisations from other languages ("part" and "pet" for Perth, "gold" for Gold Coast) that would let non-place input through; plus a hand-kept list of state and territory names and tourist destinations that are not towns (Uluru, Great Ocean Road, Blue Mountains, Kangaroo Island, Whitsundays, Great Barrier Reef, Barossa Valley, Daintree, etc.; at least every destination in the knowledge base and the evaluation dataset); plus hand-added Chinese names. The country name itself ("Australia", 澳大利亚) is not in the table. Alternatives: ABS Urban Centres and Localities (authoritative, but distributed as spreadsheets / shapefiles); the Geoscience Australia Gazetteer (~370k names including creeks and hills, so almost any input would pass).
     - **Chinese names** (revised 2026-10-31): one Chinese name per major city, state and destination, in Simplified script and its Traditional-script form (悉尼, 墨尔本 / 墨爾本, 布里斯班, 黄金海岸 / 黃金海岸, 凯恩斯 / 凱恩斯, 珀斯, 阿德莱德 / 阿德萊德, 霍巴特, 达尔文 / 達爾文, 堪培拉, 塔斯马尼亚 / 塔斯馬尼亞, etc.). Other translations of the same place are not included: one name per place keeps the list small and checkable, at the cost that a request using another translation is rejected. Alternative: Simplified only — Traditional-script input of the same name would be rejected.
     - **Reproducible build**: `scripts/build_places.py` builds the TSV from the downloaded GeoNames file and the hand-kept lists. The TSV, the hand-kept lists, the script and a source / licence note (CC BY requires attribution) are committed; the GeoNames file is downloaded by hand to `data/places/raw/cities1000.txt` (gitignored), with the download URL in the note.
     - **Normalisation before lookup**: lowercase, strip, collapse inner whitespace; when the full name is not listed, drop trailing state, territory or country qualifiers one at a time (`"Sydney, NSW"` → `sydney`, `"Hobart, Tasmania"` → `hobart`, `"Perth, WA, Australia"` → `perth`). The country qualifier is included because "Sydney, Australia" is a common way to write a city. A state left after removing a state qualifier ("Tasmania, Victoria") is rejected: it names two destinations. Whether the qualifying state is the place's own state is not checked ("Sydney, Tasmania" is accepted as `sydney`); checking it needs each place's state in the list, which is left to roadmap items 3 and 4 (a request parser can return the city and state separately). The form accepts one destination; a trip across several places is not supported.
     - **Guard against coincidences**: a unit test asserts that the foreign cities in the evaluation dataset (Paris, Tokyo, Auckland, Bali, London) are not in the table, since a low population threshold can admit a same-named Australian town.
     Alternative: English names only — the evaluation dataset's `chinese_destination` entries (form destination written in Chinese, e.g. 悉尼) would be rejected, and the behaviour correctness rate would actually drop.
   - **Prompt injection**: every free-text field is matched against a set of patterns, such as "ignore (all|previous) instructions", "system prompt", "you are now", and role markers (`<|...|>`, `### system`), ignoring case, plus Chinese equivalents such as "忽略…指令", "系统提示词" and "你现在是". The Chinese patterns are needed because this change starts accepting Chinese place names, and the evaluation dataset has a Chinese injection entry. The pattern list lives in configuration and can be extended. This is only a basic line of defence; its main purpose is to have measurable cases in the evaluation dataset.
   - **What the guards cannot catch in this change**: e058 carries its injection in `form.notes`, which is not a request field until `rebuild-rag` (`TravelRequest` drops it, so it never reaches the prompt either); e047 asks for a cover letter with a valid destination and no injection wording, which needs request understanding (roadmap item 3). No rule is added for either: a rule written for one dataset entry would be fitting the test. Both are reported in `docs/experiments.md` with the change expected to fix them. The six `prompt_injection` entries (task 6.2, reviewed 2026-10-31) cover English and Chinese instruction overrides, role switching, spoofed role markers, and injection in `destination`, `travel_style` and `notes`; none is added, because entries written after the patterns would mostly test what the patterns already match. Not covered, and not caught by the patterns: paraphrases ("act as …", "pretend the rules above don't exist"), split or encoded text, other languages, and instructions inside retrieved documents.

7. **The day-count guardrail compares against the user's requested `trip_length`** (read from the intake event); when the intake event cannot be read it falls back to checking internal consistency only.

8. **Where the "knowledge context" comes from**: validate_output takes each chunk's `chunk_text` from the `retrieved_context` of the `rag_retrieve` event and joins them as the comparison text for the "unsupported specifics" rule; it is empty when retrieval did not run. After `rebuild-rag`, chunks gain more fields but `chunk_text` stays the same, so this rule does not need to change with it.

9. **Costs are always computed as "per person, in AUD, excluding accommodation".** Both the generation and the correction templates say so (the itinerary has no stay, so including one would make the caps meaningless); the budget cap uses the "per person per day" caps that `build-evaluation-harness` defines in `config.py`, as defaults when the request gives no amount (decision 13). Template text is changed by adding new versions (old versions are not edited); old versions are kept so v0.1.0 results can be reproduced with `template_version`.

10. **Only one active version is allowed per template key.**
    - Database layer: a new migration creates the partial unique index `UNIQUE (template_key) WHERE is_active` on `prompt_templates`.
    - Seed layer: which versions exist and which one is in use are declared separately. `TEMPLATE_DEFINITIONS` lists every version (append-only); `ACTIVE_TEMPLATE_VERSIONS` maps each key to the version in use. Seed first checks that every declared version is defined (otherwise it exits with an error before writing), inserts missing versions, then in the same transaction sets every version of the key inactive and the declared one active. Upgrading is "append a version and change its number in the map"; rolling back is "change the number back", with no new rows.
      Alternatives: "the highest version is active" — rolling back would mean adding a copy of an old version under a new number, so versions pile up with duplicate text; an `is_active` flag on each definition — nothing stops two definitions of one key from both being marked active, while a map has one entry per key.
    - The declaration takes effect only when seed runs; at runtime the application still reads `is_active` from the database, and `?template_version=N` still pins a single request to any stored version.
    - The original "Seeded templates" requirement hardcoded "3 rows", which stops being true as soon as a template is upgraded, so it is replaced by "Seeded template set", which does not depend on a specific count. Later changes (e.g. `rebuild-rag`) that add template versions do not need to change this requirement again.

11. **The low-confidence case in the golden test**: change the destination from `"abcdefg hi"` to a valid Australian place name (e.g. `"alice springs"`), still using a rare travel_style to produce low confidence. During implementation, actually run it once to confirm the confidence really is below 0.85.

12. **Agno telemetry is off by default in code, with the environment variable as the override.** `travel_workflow` is constructed with `telemetry=False`, so every environment (local, deployment, evaluation runs) is off without depending on each machine's `.env`. `.env.example` gets a commented-out `AGNO_TELEMETRY=false` explaining that, when set, it overrides the code for every Agno instance — which matters once roadmap item 4 adds an `Agent`, since each Agno instance has its own `telemetry` flag. The conftest setting stays as a safety net for tests.
    Alternative: rely on `AGNO_TELEMETRY` in `.env` only — any environment that forgets it would silently send telemetry.

13. **The budget ceiling: an optional user amount for any level, the level's default otherwise.**
    - **Request** (confirmed 2026-10-28): optional `max_daily_budget_aud`, an integer of at least 1, in AUD per person per day, excluding accommodation (the same unit as decision 9); cents carry no meaning at this scale. A fractional amount is rejected with 422 like a fractional `trip_length`, not rounded: silent rounding would hide a client bug, and loosening the rule later is backward compatible while tightening it is not. The form keeps users from meeting that 422 by accepting only whole numbers and saying so. No upper bound: a mistyped amount ("20000" for "2000") only yields a visibly lavish itinerary, and whether an amount is plausible — too low for the destination, or too high — together with a loose default ceiling for `luxury`, belongs to roadmap item 4's reference price table. An input maximum was considered and rejected: below it, a `luxury` request without an amount (no ceiling) would be looser than any amount the user is allowed to type. Absent or null means "use the level's default". The intake event carries it (`null` when absent).
    - **Daily ceiling of a request** = `max_daily_budget_aud` when given, otherwise `DAILY_COST_CAP_AUD_PER_PERSON[budget]` (`budget` 70, `moderate` 200), otherwise none (`luxury`). The same function is used by the budget rule, the template variable and the evaluation harness, so the three can never disagree.
    - **The levels stay, as style.** "luxury" also means fine dining and private experiences; an amount alone loses that. When the amount and the level seem to disagree ("budget" with 500 AUD a day), the amount sets the ceiling and the level still describes the style; the request is not rejected.
    - **The templates state the ceiling** through a `{daily_budget_ceiling}` placeholder, filled with e.g. `"200 AUD per person per day, excluding accommodation"` or, without a ceiling, `"none set"`. The wording around it lives in the template in the database; code supplies only the value. Without this the model learns the number only after failing the rule, which costs a correction call per over-budget request.
    - **Not checked here**: whether the amount is realistic for the destination (30 AUD a day in Sydney). That needs a reference price table (roadmap item 4), which would let the system ask back instead of planning.
    - **Alternatives**: (a) replace the levels with the amount — loses the style signal and breaks comparison with the v0.1.0 dataset; (b) an amount only for `luxury` — an inconsistent rule, and a user cannot ask for "moderate, but at most 120 a day". The amount is chosen over a free-text budget so that the rule stays code, not a judgement.

14. **A trip is at most 14 days** (added 2026-10-31). `trip_length` above 14 is a field validation error (422 without `reason`), and the form says so before sending (`max="14"`, "Please enter a trip length between 1 and 14 days."). The limit is `MAX_TRIP_LENGTH_DAYS` in `config.py`. Output length grows with the number of days (about a hundred output tokens per day in the task 3.1 experiment): a very long trip is slow and costly, can be cut off at the model's output limit and then fails its correction too, and repeated long requests would run up the Gemini bill of a public deployment. 14 covers the trips people plan day by day; the evaluation dataset uses 1–10. Alternatives: 30 — allows month-long trips at about twice the worst-case output; only a `max_output_tokens` cap — still accepts the request and then fails it after paying for the call.

## Risks / Trade-offs

- [Embedding failures are masked by the fallback and hard to notice] → Log at error level, write `error_type="embedding_failed"` to the trace, and set `is_fallback=true` in the event.
- [Stricter rules raise the retry rate and latency] → This is exactly the cost to quantify with the evaluation harness; the report compares retry rate, error rate and p95 latency.
- [Several budget-related changes land at once, so a better "within budget" cannot be attributed] → Evaluate in three steps on separate commits: the cost-unit wording only, then the ceiling in the template, then the rules (task 6.3).
- [Dataset v2 adds entries with an amount, so the v0.1.0 baseline (v1) does not cover them] → Compare with the baseline on the 73 entries both versions share; report the new entries separately.
- [The regexes for opening hours and amounts may produce false positives or misses] → Write unit tests for every pattern; the faithfulness metric in the evaluation can reveal misses.
- [The high-confidence path has no knowledge context, so any specific price is judged unsupported] → This is the intended behaviour: prices without support should not appear in the first place. The correction prompt asks for them to be removed.
- [The place-name table wrongly rejects valid small places] → State this in the README; add one small-place entry to the evaluation dataset to observe it; the roadmap has alternatives.
- [Vague destinations ("Australia", "the east coast") are rejected instead of being asked about] → The rejection message tells the user to name a specific place; the README states it; the `clarify` entries are counted wrong by the harness either way until roadmap item 3.
- [The partial unique index migration fails on a database that already has two active versions] → The migration first sets every active row except the highest version of each key inactive, then creates the index.
- [`response_schema` does not support some Pydantic features] → Experiment with the current `ItineraryOutput` before implementing; if there are problems, hand-write an equivalent schema.
